# MMフォルダ実装と設計書（統合版V2）の相違点

**位置づけ**：本資料は「テスト知識管理のGit-nativeモデル_統合版V2.md」（以下「設計書」）と、現行のMMフォルダ実装（TODOアプリを題材にしたケーススタディ運用）を突き合わせ、確認できた相違点を整理したもの。設計書の各章番号に対応させて記載する。「ChangeEvent連動・実行状態追跡」に関する相違点への対応方針は別紙「ChangeEvent連動_実行状態追跡仕様.md」にまとめたため、本資料では概要のみ再掲し詳細はそちらを参照する。

調査範囲：`c:\Users\papa\work\mm`配下（本資料および上記仕様書自体は対象外）。

---

## 1. 全体評価

MMフォルダの実装は、設計書が核心的貢献と位置づける以下3点については骨格レベルで反映されている。

- Feature idの系譜キーとしてGitのblob SHAを使う（人間が手動でversion整数を管理しない）
- TestCaseをknowledge/から分離し、generated/配下の派生物として管理する
- ChangeEventをマイルストーン境界（Gitタグ）で自動計算する

一方、設計書がより後の版で厚く記述している「人間が介在する部分」「フォーマット保証の仕組み」の多くは未実装、または実装が外部ツール（`markharness`）のブラックボックスに委ねられており、MMリポジトリ自体からは検証できない。全体として、**中核アイデアの検証段階（プロトタイプ運用）**であり、設計書全体を反映した完成形ではない。

## 3. Feature front matterのフィールド（設計書第3.1節・第3.5節）

```yaml
# MM実装の実例（knowledge/todo-simple/todo-add/feature.yml）
id: todo-add
requirement: todo-simple
label: Todoを追加
axis: [ui, state]
```

- **`forked_from`が一度も使われていない**：4つのFeature（`todo-add`/`todo-complete`/`todo-delete`/`todo-edit`）いずれのfront matterにもキー自体が存在しない。概念的派生（fork）の実例がなく、この運用が機能するかは未検証。
- **`derived_from`はfront matterに一切現れない**：設計書の設計思想（自動導出であり人間が書く項目ではない）とは矛盾しないが、系譜情報は`.markharness-cache/*.json`（id→blob_sha）や`changes/*.yaml`の`from_blob`/`to_blob`側に間接的に表現されるのみで、Feature単体のファイルを見ても版履歴は分からない。
- **`requirement`フィールドが追加されている**：設計書の例には無いキーで、REQUIREMENTへの参照を明示している（2章で触れた階層追加に対応）。
- **`label`の使われ方が異なる**：設計書例は`label: v4`のようなバージョン風文字列だが、実装では常に日本語の機能説明文（例：`Todoを追加`）。「表示専用」という位置づけ自体は矛盾しないが、想定していた用途とは異なる。
- **`version`フィールドが無い点は設計書と一致**（意図した通り）。

## 4. ChangeEventの記録形式（設計書第3.5節）

```yaml
# 実例：changes/test2.yaml
- event_id: todo-edit--test1--test2
  feature_id: todo-edit
  from_milestone: test1
  to_milestone: test2
  from_blob: null
  to_blob: 038f700467e4e5b503251afb6d390ac053b74d5b
  impacted_testcases:
  - tc-edit-existing-todo-001
```

- マイルストーン境界での自動生成という方針は一致。
- **`change_type`（仕様変更／バグ修正等、人間が入力する想定）フィールドが存在しない**。分類情報を付与する仕組みが未実装。
- ファイル構成が設計書の例（1イベント1ファイル）とは異なり、1マイルストーン区間につき1ファイルで複数イベントを配列にまとめる形式。

## 5. TestCase / TestExecution / Milestone（設計書第3.1節・図中ER）

- `generated/testcases/*.yml`はrequirement/feature/behavior/condition/expected_resultsへの`generated_from`参照を持ち、knowledge/とは分離管理されている点は設計書と一致。
  - ただし**ファイル名と内部の`case_id`が対応していない**（例：ファイル名`todo-add-valid-title.yml`、中身`case_id: tc-todo-add-valid-title-001`）。設計書例はファイル名とcase識別子がほぼ一致する命名だった。
- `executions/<milestone>/milestone.yml`は`id: test1`のような1行のみで、日付・説明等のメタ情報を持たない。設計書はマイルストーンのメタ情報保持を明示していないため矛盾ではないが、最小限の実装にとどまっている。
- `results.yml`は`case_id / result / executor / executed_at`のみを保持し、実行時点でのFeature版情報を持たない。この点への対応は別紙「ChangeEvent連動_実行状態追跡仕様.md」で仕様化した。
- マイルストーンはGitタグ（`test1`/`test2`/`test3`）と対応づけて運用されている。設計書はGitタグとの対応関係を明示していないが、矛盾はない。

---

## 6. Axis（横断的観点）の管理（設計書第3.1節・第3.5節）

- `axes/ui.yml`・`axes/state.yml`・`axes/validation.yml`が実在し、`id`と`label`のみの最小限の内容。レジストリとして`knowledge/`から分離されている点は設計書と一致。
- Feature側の`axis`値（`ui`/`state`/`validation`）は目視では`axes/`配下の定義と矛盾なく一致している。
- ただし**「axes/*.ymlに定義されていない値をスキーマバリデーションで弾く」という設計書の方針が実際に機能しているかは確認不能**（`schema/`が空のため）。バリデーションが本当に働いているのか、単に値が偶然一致しているだけなのか区別がつかない。

---

## 7. id解決キャッシュ（設計書第3.3節）

- `.markharness-cache/test1.json`等が実在し、`.gitignore`で除外されGit管理下に無い。「id解決キャッシュは非コミット化する」という設計書の方針とは**一致**。
- ただし配置場所がリポジトリ直下の`.markharness-cache/`であり、設計書が言及する（旧配置としての）`generated/id-index.json`とは異なるパス。設計書には新配置の具体例が無いため、これ自体は矛盾ではなく単なる相違点。
- キャッシュの中身は`id / path / blob_sha`の単純な対応表のみで、設計書第3.3節が挙げる`canonicalization_rule_version`・`id_index_schema_version`・`tool_version`を含むキャッシュキー構造は確認できず、より単純な実装になっている。

## 8. ChangeEvent連動・実行状態追跡（設計書第3.5節・図4）

「変更があったのに未実行のテストはどれか」「この結果はどの変更の後の実行か」を自動で答える機能が、現行実装には存在しない（`results.yml`と`changes/*.yaml`を人間が目視で突き合わせている）。この相違点への対応は仕様化済み。詳細は別紙「[ChangeEvent連動_実行状態追跡仕様.md](./ChangeEvent連動_実行状態追跡仕様.md)」を参照。

**追記（markharness側の修正について）**：本資料が観測した`.markharness-cache/*.json`の`id / path / blob_sha`という構造（第7節）は、当時のmarkharness実装が**Featureの変更検知をfeature.yml単体ファイルのblob SHAでのみ判定していた**ことによるものだった。この実装では、Condition・Behavior・ExpectedResultを追加・変更してもfeature.yml自体が不変であれば変更が検知されない不具合があった。markharness側は`id_cache::resolve_feature_versions`（旧`resolve_feature_blobs`）をFeatureディレクトリ全体のtree SHA比較に変更し修正済み（`blob_sha`→`tree_sha`、`FeatureBlob`→`FeatureVersion`等、関連する命名も刷新）。本資料が調査したMMリポジトリ側のデータ自体は当時のスナップショットとして書き換えていない。

## 9. 総括

| 分類 | 状況 |
|---|---|
| 実装済み・設計書と一致 | blob SHAベースの系譜キー、TestCaseの派生物としての分離管理、ChangeEventのマイルストーン境界自動生成、idキャッシュの非コミット化 |
| 未実装（設計書には記述があるが実体なし） | `forked_from`運用、`change_type`入力、`schema/`によるバリデーション実体、`tools/`のリポジトリ内コミット、ChangeEventと実行結果の自動突合 |
| 設計書に無い追加要素 | REQUIREMENT明示ファイル、`tmp/`作業領域、Feature front matterの`requirement`キー |
| 命名・粒度の相違（機能的な矛盾ではない） | `changes/`のファイル粒度・拡張子、TestCaseファイル名とcase_idの不一致、idキャッシュの配置パス |

MMフォルダは、設計書のうち「版履歴DAG」「TestCase派生」「ChangeEvent自動化」という中核部分の実現可能性を検証する目的では機能しているが、査読論文としての貢献として掲げられている「人間介在部分の明確化」「フォーマット保証」「変更影響の再確認漏れ検知」は、まだ実装・検証の途上にある。
