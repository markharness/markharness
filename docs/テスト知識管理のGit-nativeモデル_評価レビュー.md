# テスト知識管理のGit-nativeモデル：評価レビュー

対象：`テスト知識管理のGit-nativeモデル_統合版.md` および `markharness` 実装  
評価日：2026-08-13(2026-08-12版レビューの指摘反映状況を再評価した改訂版。旧版の内容はこの版に一本化した)

## 結論

統合版は、前回レビューで指摘した既存TMSへの過度な断定、永続的なVersion DAGと実装の不整合、Condition単位の影響分析を示唆する図表を、概ね適切に是正している。とりわけ、**マイルストーン区間のChangeEventモデル**へ主張を限定し、Feature単位の保守的な候補抽出であること、RQ1は未実証の仮説であることを明記した点は改善である。

現時点では、設計提案＋リファレンス実装としてTool Demo／アーキテクチャ提案トラックに投稿できる水準に近づいている。一方で、ESEM・ICSME・SANER等で実証研究として投稿するには、関連研究の一次文献に基づく再構成、ブランチ戦略に関する主張の限定、再現可能な評価プロトコルがなお必要である。総合判断は **大幅改訂（major revision）** とする。

## 論文の評価

### 強み

1. **設計と実装の境界を明確にした**
   - `derived_from`を永続DAGの辺ではなく、マイルストーン間のtree SHA比較から導出する概念として定義している。
   - §3.6で実装済み・簡略化・未実装を分け、RQ1が未実施の評価計画であることも結論まで一貫して明示している。

2. **変更検知の単位を実態に合わせた**
   - Featureディレクトリ全体のtree SHAを比較し、`feature.yml`以外のConditionやExpectedResultの変更も検出する。
   - 影響候補はFeature配下の全TestCaseを返す保守的な抽出であり、細粒度化を将来課題に切り分けている。

3. **履歴再現性への配慮が進んだ**
   - `changes compute`の既定を`to_milestone`時点の知識からの候補生成にし、後日の作業ツリー変更で過去区間の結果が変わる問題を抑えている。
   - ChangeEventとTestExecutionを独立した事実として記録し、pending/staleを導出する設計は監査可能性に寄与する。

### 主要な指摘

#### P0: 関連研究・製品比較を「未確認の不在」から「検証可能な比較」へ改める

§2.1〜2.3は各領域を1段落で扱っており、「既存研究が扱わない」「版履歴の第一級モデル化は扱っていない」という中心的な新規性主張を支えるには不足している。§2.4も、TestRail以外の商用TMS、GTM、tmt/fmfについて、公開文書の一部だけを根拠に「なし」「横断クエリ不可」と結論している。未検証のプラグイン、API、ソースコード、組合せ運用が残る以上、機能不在を一般論として述べるのは危険である。

- リスク：査読者が近接研究や製品機能を1件示すだけで、問題設定と差分の双方が弱く見える。
- 対応案：
  1. テスト資産進化・構成管理、変更影響分析、テストトレーサビリティ、Git管理型テスト資産の一次文献を系統的に調査する。
  2. 比較表の各セルに典拠と確認範囲を付け、「機能がない」ではなく「調査した公式文書・版・設定では確認できなかった」と記述する。
  3. 差分を製品全般への優位性ではなく、**Gitタグ間のFeature tree SHA差分からChangeEventと再検証状態をローカルに導出する参照実装**へ限定する。

#### P0: 「ブランチ戦略に依存しない」を分解して主張する

本文はtree SHAと`git merge-base`により「ブランチ運用に依存せず」と述べる。しかし、squash mergeでは元ブランチの親子関係・中間コミットがGit履歴に残らず、`true_divergences`を復元できない。rebaseでも元のコミットIDは失われる。マイルストーン間の最終状態差分は計算できるが、分岐由来の監査情報まで同じ精度で得られるわけではない。

- 対応案：
  - 「最終tree差分のChangeEvent生成はブランチ戦略に依存しない」と、「Git履歴に残るマージの系譜監査はmerge commitを必要とする」を分けて明記する。
  - squash/rebase/fast-forward/merge commitの各戦略について、得られる出力と失われる情報を表にする。
  - RQ1の対象を最終状態の変更影響識別に置くなら、`true_divergences`は副次的な監査機能として評価対象外であることを明確にする。

#### P1: 「知識グラフ」および`derived_from`の表現をさらに整合させる

タイトルはVersion-Aware Knowledge Graph Modelであり、ER図と図2は`derived_from`をFeature間の矢印として描く。一方、実装はその版ノード・辺を保存せず、独立したChangeEvent差分ログを持つ。この注記はあるが、読者には永続的にクエリ可能なグラフを提供するように読める余地が残る。

- 対応案：タイトルを「Git-native ChangeEvent Model for Test Knowledge Management」等へ寄せる、または少なくとも冒頭で「知識グラフ」は静的な構造・Axis関係を指し、版履歴はグラフの保存ではなく差分イベント列であると定義する。
- 図2は概念図であることを明示し、実装の永続データ（`changes/<to_milestone>.yaml`）と対応づける図を併記する。

#### P1: 評価計画を被験者内の再現可能な実験プロトコルへ進める

層α／層β、現状運用を対照にする方針は妥当である。ただし、層βを「対照群が原理的に対応不能」と定義すると、結論を前提にした課題選定になりうる。さらに、群あたり15〜30名という目安だけでは、被験者間・被験者内のどちらか、順序効果、訓練、検定、欠測処理が定まらない。

- 対応案：
  - 「深い変更」を、リリース間隔・変更回数・関連Feature数・マージ有無など観測可能な基準で事前固定する。
  - 被験者内クロスオーバーを基本候補とし、ツールと課題の順序をカウンターバランスする。
  - 効果量・有意水準・検出力から必要サンプル数を算出し、主分析（例：層βのF1または適合率・再現率）と多重比較の扱いを事前登録する。
  - 対照群にも、実務で通常利用できるGit履歴・TMS履歴・検索機能を全て使わせる。

#### P1: 正解データではco-changeを候補信号に留める

§5.4はノイズ除去と複数専門家の確認を導入しており前進している。しかし、同じコミット／PRで変更されたテストは「実際に影響を受けた」ことの十分条件ではない。さらに、提案モデルの生成関係との一致を採用条件に含めると、提案手法に有利なオラクルになる可能性がある。

- 対応案：co-change、仕様・Issue・PRレビュー、CIログを独立した証拠種別として保存し、モデル由来の構造情報を見ずに評価者が真値を判定する工程を置く。候補抽出と真値確定を分離し、除外・部分点・不一致解決の規則を事前登録する。

## ツールの評価

### 強み

- READMEに最小チュートリアル、タグの前提、Git notes同期、未実装インポータを記載しており、前回の利用者向け導線の欠落は解消されている。
- `changes compute`はhistoricalを既定とし、`--current-tree`を明示的な代替モードにしたことで、過去のChangeEventの再計算意味論が明瞭になった。
- tree SHAによるFeature変更検知、`changes lineage`の真の分岐監査、`verify trace`／`verify pending`の実装とテストが存在する。

### 主要な指摘

#### P1: 実行記録の入力検証と移行方針を完成させる

`executions/*/results.yml`にはJSON Schema検証がなく、導入前の実行記録は「不明」として遡及判定できない。このままでは、再検証追跡という実運用上の価値が、新規導入後の記録に限られる。

- 対応案：実行結果用のスキーマと整合性検証を追加する。旧記録については、明示的にunknownを保持する移行コマンド、または信頼度付きのバックフィル方針を仕様化する。

#### P1: 大規模・共同運用の主張は実測で裏付ける

Git notesを用いた進捗管理とオンデマンドバックフィルの設計は合理的だが、実リポジトリでの履歴規模別の時間、キャッシュヒット率、並行実行、notes同期失敗時の復旧を検証していない。本文の「大規模リポジトリへの段階的導入可能」という貢献は、現時点では仮説に留まる。

- 対応案：少なくとも1件の既存リポジトリで、初回バックフィル時間、増分処理時間、ストレージ量、運用手順、失敗・再実行をケーススタディとして報告する。

#### P2: ID変更とハッシュ／キャッシュ仕様の境界を利用者向けに明記する

パス変更には耐える一方、`feature.yml`内の`id:`を変更した場合は同一Featureとして追跡できない。加えて、正規化ルールとキャッシュ形式の版番号は固定値である。これらは設計上既知だが、識別子変更を行う利用者にはデータ断絶として現れる。

- 対応案：CLIマニュアルにID不変性を明記し、変更時の移行手順または明示的な後継Feature／エイリアス機構を設ける。キャッシュ形式更新時の互換性方針も定義する。

## 推奨する進め方

1. 一次文献と公式資料に基づき、関連研究・製品比較表を再構成する。
2. 最終状態のChangeEvent生成と、merge commitに依存する系譜監査を分離して記述する。
3. 知識グラフ／ChangeEvent差分ログ／永続DAGの用語と図を整理する。
4. 被験者内比較、タスク基準、オラクル、検出力を含む評価プロトコルを事前登録する。
5. 実行記録のスキーマ、ID変更の方針、大規模共同運用のケーススタディを補強する。

この順序で進めれば、短期的にはツール提案として主張を堅く保ちつつ、中期的にはRQ1を検証可能な実証研究へ発展させられる。
