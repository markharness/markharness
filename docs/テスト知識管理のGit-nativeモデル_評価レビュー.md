# テスト知識管理のGit-nativeモデル：評価レビュー

対象：`テスト知識管理のGit-nativeモデル_統合版.md` および `markharness` 実装  
評価日：2026-08-12

## 結論

本研究は、Gitの履歴と構造化したテスト知識を結び、変更後に再確認すべきテストを追跡するという実務的に価値の高い問題を扱っている。現時点では、**設計提案＋リファレンス実装としては有望**であり、Tool Demo／アーキテクチャ提案トラックへの投稿候補になり得る。

一方、ESEM・ICSME・SANER等で実証研究として主張するには、比較主張の精密化、モデルと実装の整合、実データによる評価が必要である。総合判断は **大幅改訂（major revision）** とする。

## 論文の評価

### 強み

1. **問題設定が実務に根ざしている**
   - 「過去の変更から、現在再確認すべきテストを辿る」という問いは、リリースをまたぐ保守で実際に生じる。
   - RQ1を変更影響識別タスクに絞り、浅い変更と深い変更を分ける方針は、提案手法が効く場面を明確にする。

2. **未実証であることを明示している**
   - RQ1を検証済みの結論ではなく仮説として扱っており、設計提案と実証結果を混同していない。
   - 実装との差異・未実装事項を本文で開示している。

3. **実装上の設計判断に一貫性がある**
   - Featureディレクトリ全体のtree SHAを変更単位にし、Feature定義ファイル以外の変更も検知する。
   - キャッシュをGit管理対象外とし、キー不一致時に再構築する。
   - ChangeEventとTestExecutionを別々の事実として持ち、再検証状態を導出する。

### 主要な指摘

#### P0: 既存TMSに関する断定を修正する

本文は既存TMSを「現時点のスナップショット中心」「複数世代の派生関係を扱えない」と広く断定している。しかし、TestRail Enterpriseはテストケースの履歴比較と復元を提供している。したがって「既存ツールに版管理機能がない」という主張は成立しない。

- 対応案：
  - 製品一般への断定を避け、比較対象を機能単位で記述する。
  - 本研究の差分を、**Gitのコミット意味論、構造化テスト知識、マイルストーン境界のChangeEvent、再検証追跡を統合したローカル／Git-native運用**と定義する。
  - TestRail、Xray等については、公式資料で確認できる範囲だけを比較表に記す。

参考：TestRail公式「Test case versioning」  
https://support.testrail.com/hc/en-us/articles/7768433966996-Test-case-versioning

#### P0: 「Version DAG」の主張と実装を一致させる

本文は`derived_from`を持つVersion DAGを中核貢献と位置付ける。一方、主実装の`changes compute`は2つのマイルストーンタグにおけるtree SHAの差分を`ChangeEvent`として保存する。真の分岐は`true_divergences`という監査情報として記録されるが、版ノードと`derived_from`辺を持つ独立した永続DAGではない。

- リスク：査読者には「DAGを提案したのか、マイルストーン差分ログを提案したのか」が曖昧に見える。
- 対応案（いずれかを選ぶ）：
  1. 現実装に合わせ、中心概念を「Git履歴から導出するマイルストーン区間のChangeEventモデル」に改める。
  2. DAGを中心概念として維持するなら、版ノード、辺、マージ時の親、保存形式、クエリ意味論を明示し、実装にも反映する。

#### P0: 影響範囲の粒度を正しく説明する

本文の図はCondition単位で影響あり／なしを分ける。しかし実装は、変更されたFeatureに対応する現在の全TestCaseを`impacted_testcases`として取得する。Condition単位の変更原因解析は行っていない。

- リスク：本文の「適合率・再現率を改善する」という主張に対し、適合率低下を招く過大な候補集合が生成される可能性がある。
- 対応案：
  - 現行機能を「Feature単位の保守的な候補抽出」と明記する。
  - Condition／Expected Resultの差分を用いた精密化は別RQまたは将来課題に分離する。
  - 実験では候補数、適合率、再現率を併記する。

#### P1: 正解データの定義を強める

co-changeは有用な候補信号だが、テストが本当に変更の影響を受けたかの真値そのものではない。束ねたコミットやリファクタリングに起因する偽陽性が残り得る。

- 対応案：
  - co-changeを候補生成に限定する。
  - 仕様、PR、レビュー記録を根拠に、独立した複数評価者が最終オラクルを確定する。
  - 不一致の扱い、除外基準、部分点、Cohen's kappa、適合率・再現率の集計方法を事前登録する。

#### P1: 評価計画を実験プロトコルまで具体化する

層別化と実運用を対照群にする方針は良いが、現状では「群あたり15〜30名」という目安だけで、比較デザインが定まっていない。

- 対応案：
  - 被験者内クロスオーバーを基本候補にし、ツール順序・課題順序をカウンターバランスする。
  - タスク、正答定義、制限時間、訓練時間、除外規則、分析方法を事前登録する。
  - 対照群が実際に使える情報を具体的に固定する。Git履歴・TMSの版履歴などを恣意的に隠さない。
  - 「深い変更」の定義を、リリース数・変更回数・ブランチ有無など再現可能な条件で記述する。

#### P1: 関連研究と参考文献を再構成する

現在の参考文献は製品比較ブログの割合が高く、関連研究の網羅性と査読耐性が弱い。テスト資産の構成管理・変更影響分析・テストトレーサビリティ・Git-native test managementを系統的に比較する必要がある。

- 対応案：
  - 各先行研究について、対象成果物、履歴モデル、Git統合、変更影響分析、実証方法を比較する表を作る。
  - 製品機能は公式ドキュメント、学術的主張は一次論文を引用する。
  - 「版間関係を持つテスト成果物と変更影響分析」は既存研究にもあることを認め、その上で本手法の差分を限定的かつ検証可能な形で主張する。

参考：STACMSはテスト成果物の版進化、版間関係、変更影響分析を扱う既存例である。  
https://www.ecice06.com/EN/10.3969/j.issn.1000-3428.2006.23.026

## ツールの評価

### 強み

- `init`、知識編集、TestCase生成、スキーマ検証、変更イベント計算、バックフィル、実行結果記録、再検証追跡までの機能が揃っている。
- Featureディレクトリ全体のtree SHAで検知するため、ConditionやExpected Resultのみの変更を見落とさない。
- `validate`によるJSON Schema検証と、axis／`forked_from`の相互参照検証がある。
- 自動テスト235件がすべて成功し、`cargo clippy --all-targets -- -D warnings`も成功した。

### 主要な指摘

#### P0: 利用者向けドキュメントがない

リポジトリ直下のREADMEは汎用AI開発テンプレートの説明であり、`markharness` の導入方法、最小構成、コマンド例、CI連携、運用上の制約を説明していない。

- 対応案：
  - READMEをツール専用に置き換える、または明確な入口を追加する。
  - 「初期化 → 知識登録 → 生成 → マイルストーン → changes compute → verify pending」の最小チュートリアルを載せる。
  - 既存TMSからの移行可否、Gitタグの前提、Git notesの同期方法、未対応事項を明記する。

#### P1: 履歴再現と現在の候補抽出を分離して仕様化する

`changes compute`は過去の2タグを比較するが、影響TestCase集合は現在の作業ツリーから生成する。そのため、同じ過去の区間を後日再計算すると、現在のテスト構造の変化に応じて結果が変わり得る。

- 対応案：
  - 「過去時点の影響」を答えるモードでは、`to_milestone`時点の知識からTestCaseを生成する。
  - 「現在再確認すべきテスト」を答えるモードでは、現在の知識から候補を求めることを明示する。
  - 両モードの出力・保存・再計算の意味を仕様書に記載する。

#### P1: 大規模・チーム運用の検証が未完了

- バックフィル性能、キャッシュヒット率、履歴規模別の実行時間を計測していない。
- Git notesは通常のpush／fetchで自動同期されないため、共有リポジトリでの運用手順が必要である。
- 既存TMSインポータが未実装で、導入コストを評価できない。

対応案：実リポジトリ1件以上で、初期導入時間、バックフィル時間、通常運用時の増分時間、必要なGit設定をケーススタディとして記録する。

#### P2: リリース品質の補強

- 実リポジトリを用いたエンドツーエンドの受入テストを追加する。
- `executions/*/results.yml`のスキーマ検証を追加する。
- バージョニング、ライセンス、変更履歴、互換性方針、サンプルデータセットを整備する。

## 推奨する進め方

1. 本文から「既存TMSにはない」「Version DAG」という過度な断定を取り除き、実装と一致する貢献記述へ直す。
2. Feature単位の保守的な影響候補抽出であることを明記する。
3. 既存製品・先行研究との比較表を、公式資料と一次文献に基づいて作る。
4. 実リポジトリのケーススタディと、事前登録した被験者実験を実施する。
5. ツール専用READMEと最小チュートリアルを整備する。

この順序なら、短期的にはTool Demoとしての完成度を上げながら、中期的にはRQ1を実証する研究へ自然に発展できる。
