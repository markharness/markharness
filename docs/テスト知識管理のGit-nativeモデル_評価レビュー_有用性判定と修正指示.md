# 評価レビュー(2026-08-13版)の有用性判定と修正指示

対象：`docs/テスト知識管理のGit-nativeモデル_評価レビュー.md`
判定日：2026-08-12

## 結論

このレビューは「学術論文としての査読対応」を評価軸にしている。指摘のうち、被験者内実験プロトコルの精緻化・co-changeオラクル構築の厳密化・論文タイトルの変更は、markharnessというツールの設計・実装の質には寄与しないため無用と判断する。査読耐性を上げることと、ツールの有用性を上げることは別の目的であり、本プロジェクトの方針(常に最善のプロダクトを目指す、有用性/無用性で判断する)に照らした結果である。

関連研究・製品比較の精緻化(P0-1)は、査読対応としては上記と同じ性質を持つが、ユーザーから「この比較は欲しい」との指示を受け、有用側に再分類した。競合(TestRail、GTM、tmt/fmf等)が実際に何を提供していないかを裏付けを持って把握することは、README等での差別化主張の正確性、および今後の設計判断(既存機能を車輪の再発明していないかの確認)に資するため、プロダクト設計の観点でも有用と判断できる。

一方、ツールの評価セクションの指摘、および論文の評価セクションでも「実装の挙動に関する記述の正確性」に関わる指摘(ブランチ戦略の限定、知識グラフ用語の整合の一部)は、利用者が実際にツールを使う際の正確性・信頼性に直結するため有用と判断する。

有用と判定した項目を優先度順に「修正指示」としてまとめた。無用と判定した項目は理由とともに却下する。

## 判定基準

プロジェクトの設計ルール(有用性/無用性で判断する、実装コストの多寡は判断材料に含めない、最善のプロダクトを目指す)に基づき、各指摘を以下の軸で判定する。

- markharnessというツールの機能・挙動・ドキュメントの正確性/信頼性/使いやすさを直接改善するか → 有用
- 査読者の納得(新規性の防御、実証研究としての体裁)にのみ資し、ツール自体を変えないか → 無用

「無用」は指摘内容が事実として誤りという意味ではなく、本プロジェクトの目的(プロダクト設計の検討)に対する寄与がないという意味である。

## 個別判定

### 論文の評価

**強み(1〜3)**：有用(確認事項、追加対応不要)。境界の明確化・変更検知単位の実態合わせ・historical既定化は、いずれも既に実装済みの設計判断であり、レビューはそれを追認しているだけである。

**P0: 関連研究・製品比較を「未確認の不在」から「検証可能な比較」へ改める**：有用(ユーザー指示により再分類)。

一次文献の系統的調査、比較表の各セルへの典拠付与、「機能がない」を「調査した範囲では確認できなかった」に弱める言い回しの精緻化は、査読者が近接研究・製品機能を1件示した場合の防御力を上げる、という点では査読対応の性質を持つ。`docs/improvement-prompts.md`の項目8もその観点で低優先度としていた。

一方で、この比較作業自体は競合の実際の機能を裏付けを持って把握する作業であり、その成果物(比較表・典拠)はプロダクト向け文書(README、差別化を説明する箇所)にもそのまま転用できる。ユーザーからこの比較を残したいとの指示があったため、目的を「査読対応」ではなく「競合把握・差別化主張の正確性確保」に読み替えて有用側に分類する。

**P0: 「ブランチ戦略に依存しない」を分解して主張する**：有用。

squash mergeでは元ブランチの親子関係が失われ、`true_divergences`(真の分岐)を復元できないという指摘は、ツールの実際の挙動に関する正確性の問題である。「ブランチ運用に依存せず版履歴を導出する」という記述だけを読んだ利用者が、squash運用のチームで`changes lineage`(分岐監査)も同じ精度で動くと誤解する余地がある。これは査読対応ではなく、CLIマニュアル・READMEの正確性の問題として扱うべきである。

**P1: 「知識グラフ」および`derived_from`の表現整合**：部分的に有用。

論文タイトルを「A Version-Aware Knowledge Graph Model」から変更するかどうかは、打ち出し方の問題でありツール設計には影響しない(無用)。一方、`derived_from`が永続グラフではなく差分イベント列であることをプロダクト向け文書(README、cli-manual.md)で明示することは、利用者が「クエリ可能な永続グラフがある」と誤解して機能を探し回ることを防ぐため有用である。

**P1: 評価計画を被験者内の再現可能な実験プロトコルへ進める**：無用。

サンプルサイズの検出力計算、被験者内クロスオーバー、多重比較の事前登録は、RQ1を学術的に実証するための手続きであり、ツールの設計には影響しない。ツールが実際に役立つかどうかを確認する手段としては、正式な統計的検証よりも実運用でのdogfooding・利用者からの継続的なフィードバックの方が低コストで直接的である。

**P1: 正解データではco-changeを候補信号に留める**：無用。

理由は上記と同じ。被験者実験そのものを実施しない限り、オラクル構築手順の厳密化は意味を持たない。

### ツールの評価

**強み**：有用(確認事項、追加対応不要)。

**P1: 実行記録の入力検証と移行方針を完成させる**：有用。

`executions/*/results.yml`にJSON Schema検証がないという指摘は、`verify trace`/`verify pending`という中核機能のデータ整合性に直結する。不正な実行記録が検知されずに`changes/*.yaml`との突合に使われると、pending/stale判定という監査可能性の核心が静かに壊れる。学術的な指摘ではなく、実装の欠落である。

**P1: 大規模・共同運用の主張は実測で裏付ける**：条件付きで有用。

バックフィルアーキテクチャ(第4章)が実測なしの仮説のままであるという指摘自体は正しい。ただしこれは設計の変更を要求するものではなく、既存設計の妥当性を実データで検証する作業であり、優先度は他の項目より低くてよい。「大規模リポジトリへの段階的導入が可能」という文言をドキュメントに残すのであれば、根拠のない主張として弱めるか、検証を実施するかのどちらかを選ぶ必要がある。

**P2: ID変更とハッシュ/キャッシュ仕様の境界を利用者向けに明記する**：有用。

`feature.yml`の`id:`を変更すると同一Featureとして追跡できなくなる、という制約は設計上の既知事項だが、利用者向けドキュメントに明記されていない。実際にIDを変更した利用者が履歴の断絶に気づかず使い続けるリスクがあり、これはツールの安全な利用に直結する。

### 推奨する進め方(1〜5)への判定

1. 関連研究・製品比較の再構成 → 有用(P0-1と同じ、ユーザー指示により再分類)
2. ChangeEvent生成とmerge commit依存の系譜監査の分離記述 → 有用(P0-2と同じ)
3. 知識グラフ/ChangeEvent差分ログ/永続DAGの用語整理 → 部分的に有用(プロダクト向け文書に限る)
4. 被験者内比較・タスク基準・オラクル・検出力を含む評価プロトコルの事前登録 → 無用(P1評価計画・正解データと同じ)
5. 実行記録スキーマ、ID変更方針、大規模共同運用のケーススタディ補強 → 有用

## 修正指示(有用と判定した項目、優先度順)

### 1. 「ブランチ戦略に依存しない」の主張を分解する【優先度: 高】

- 対象：`docs/テスト知識管理のGit-nativeモデル_統合版.md` §1.3・§3.4、`docs/cli-manual.md`
- 内容：
  - 「マイルストーン境界の最終tree差分によるChangeEvent生成」はブランチ戦略(merge/rebase/squash)に依存しないこと、「`changes lineage`によるマージの系譜監査(`true_divergences`)はマージコミットの保持を必要とすること」を分けて明記する。
  - squash / rebase / fast-forward / merge commitの各戦略について、`changes compute`(主系譜)と`changes lineage`(監査)それぞれで得られる出力と失われる情報を表にする。
  - RQ1(第5章)の評価対象が最終状態の変更影響識別である旨は既に本文にあるため、その記述と表を対応づける。

### 2. `executions/*/results.yml`のJSON Schema検証を追加する【優先度: 高】

- 対象：`schema/`、`markharness validate`
- 内容：
  - 実行結果(`case_id` / `result` / `executor` / `executed_at` / `verified_feature_tree_shas`)用のJSON Schemaを追加し、`markharness init`の既定スキーマ一式・`markharness validate`の検証対象に含める。
  - 本仕様導入前の既存実行記録(`verified_feature_tree_shas`を持たない)を明示的に`unknown`として扱う移行コマンド、または信頼度付きのバックフィル方針を仕様化する。

### 3. IDの不変性とキャッシュ仕様の境界を利用者向けに明記する【優先度: 中】

- 対象：`docs/cli-manual.md`、`docs/README.md`
- 内容：
  - `feature.yml`の`id:`を変更すると同一Featureとして追跡されなくなることを明記する。
  - `canonicalization_rule_version` / `id_index_schema_version`が現状固定値であり、実際の改訂運用が未検証であることを明記する。
  - ID変更時の移行手順、または明示的な後継Feature/エイリアス機構の要否を検討し、方針を決定する(検討結果は`docs/decisions/`に記録)。

### 4. プロダクト向け文書での「知識グラフ」表現を整理する【優先度: 低〜中】

- 対象：`docs/README.md`、`docs/cli-manual.md`(統合版.mdの論文タイトルは対象外)
- 内容：`derived_from`は永続的にクエリ可能なグラフではなく、マイルストーン境界の差分イベント列(`ChangeEvent`)であることを、利用者が最初に読むドキュメントで明示する。

### 5. 大規模リポジトリでのバックフィルケーススタディ【優先度: 低、任意】

- 対象：実データでの検証(対象リポジトリの選定が前提)
- 内容：初回バックフィル時間・増分処理時間・ストレージ量・Git notes同期失敗時の復旧手順をケーススタディとして記録する。
- 位置づけ：学術的な実証ではなく、「大規模リポジトリへの段階的導入が可能」という現行の記述の根拠を実運用リスクの観点から確認する作業として実施する。実施しない場合は、該当の記述を仮説である旨がわかるように弱める。

### 6. 関連研究・製品比較を検証可能な比較へ改める【優先度: 中】

- 対象：`docs/テスト知識管理のGit-nativeモデル_統合版.md` §2.4、`docs/README.md`(差別化を説明する箇所があれば)
- 内容：
  - テスト資産の構成管理・変更影響分析・テストトレーサビリティ・Git-native test managementの一次文献・公式ドキュメントを調査し、比較表(表1)の各セルに典拠と確認範囲(公式文書のみ確認/ソース未確認等)を付す。
  - 「機能がない」という断定を、確認できた範囲を明示した記述に置き換える(既に§2.4のGTM/tmt/fmf部分・TestRail注1で採用済みの書き方を他の行にも展開する)。
  - 出典の妥当性(実際にその主張をしているか)は一次資料を確認してから追記する。未確認のまま引用しない(`docs/improvement-prompts.md`項目8の作業手順をそのまま踏襲できる)。
  - 成果物(比較表・典拠付き記述)は、README等プロダクト向け文書での差別化説明にも転用する。

## 却下(無用と判定、対応しない)項目

- **被験者内実験プロトコルの精緻化・事前登録**(P1、推奨4)：RQ1の学術的実証のための手続きであり、ツール設計には影響しない。
- **co-changeオラクル構築手順の厳密化**(P1)：上記と同じ理由。被験者実験を実施しない限り無意味。
- **論文タイトルの変更**(P1の一部)：打ち出し方の問題であり、プロダクト設計そのものへの影響はない。

## 付記：レビューの前提そのものについて

このレビュー、および過去の変更履歴(2026-08-09〜2026-08-13の一連の対応)を見る限り、`統合版.md`はESEM/ICSME/SANER等への論文投稿を前提として書かれており、レビューもその前提で評価している。`docs/improvement-prompts.md`は既にこの構造に気づいており、査読対応系の項目(7〜10)を実験実施の意思決定にゲートしている。

本プロジェクトの方針(後方互換性を想定せず常に最善のプロダクトを目指す、設計の有用性/無用性を検討する)に照らすと、論文投稿を継続する意思が明確でない限り、今後のレビュー対応は「ツールとしての正確性・信頼性」を基準に取捨選択し、査読対応系の指摘は`improvement-prompts.md`の運用方針通り、実施の意思決定があるまで着手しないことを推奨する。論文投稿自体を続けるかどうかは設計判断の範囲外(プロダクトの方向性の話)のため、必要であれば別途意思決定として記録することを勧める。
