# Knowledge From Code (standalone)

> This file is self-contained — copy it alone into any project (or paste its
> body directly into a chat with an AI coding assistant) and it works without
> any other file from the `markharness` template repo. The only external
> requirement is the `markharness` CLI itself (see Phase 0).
>
> Respond in the language the user is using in the chat.

You will read existing source code and derive `markharness` test knowledge
from it, then generate `TestCase` data with `markharness generate`. This is
AI-assisted authoring of test knowledge
(`knowledge/**/{feature,condition,expected/*}.yaml`), not a replacement for
human review: every derived Condition/ExpectedResult must be traceable to a
specific place in the code.

## Progress tracking (inline checklist rules)

Before starting, create `checklist-knowledge-from-code.md` in the project
root:

```markdown
# Task: Derive knowledge/ from <target code>

Created: <date>

## Steps

- [ ] <one line per Behavior you plan to extract>

## Notes

<context, decisions, blockers>
```

- Mark a step `- [x]` immediately after finishing it, not in a batch later.
- If a step turns out unnecessary, mark it `- [~] Skipped: <reason>` instead
  of deleting it.
- When every step is done, add a `## Summary` section (see Phase 5).

## Data model (for reference — no other file needed)

```text
knowledge/
└── <requirement>/
    ├── requirement.yml
    └── <feature>/
        ├── feature.yml       # requirement: <requirement>
        └── <behavior>/
            ├── behavior.yml
            └── <condition>/
                ├── condition.yml
                └── expected/
                    └── 001.yml, 002.yml, ...

axes/                  # cross-cutting axis registry, one axes/<id>.yml per axis
generated/testcases/   # <requirement>/<feature>/<behavior>/<condition>.yml, deterministically regenerated by `markharness generate` — never hand-edit
```

## Procedure

### Phase 0 — Confirm the tool is available

1. Run `markharness --version` (or `--help`). If the command is not found,
   stop and tell the user: they need to build/install `markharness` first
   (from its repo: `cargo install --path .`, or use a prebuilt binary), or
   confirm they actually meant a different tool. Do not attempt to fabricate
   its output or proceed without it.
2. Check whether the target directory already has `knowledge/`, `axes/`, and
   `schema/` (i.e. `markharness init` has run there). If any are missing,
   run `markharness init --dir <target>` first — it creates the required
   subdirectories plus the default `schema/*.schema.json` files that
   `markharness validate` needs, without touching anything that already
   exists.
3. On a brand-new project, `axes/` will be empty, so _every_ axis you plan
   to use must be created (Phase 2) before drafting — there is no
   pre-existing registry to fall back on.

### Phase 1 — Scope

1. Identify the target code (file/module/function the user pointed at, or
   ask if unclear).
2. Confirm the `requirement` this code belongs to (an existing
   `knowledge/<requirement>/` id, or a new one to create — on a fresh
   project this is always new).
3. Fill in the checklist file created above with one step per Behavior you
   plan to extract.

### Phase 2 — Analyze code

For the target code, read it and identify, per public function/branch/error
path:

- **Feature**: the user-facing capability the code implements.
- **Behavior**: one distinct thing the Feature does (e.g. one function, or
  one responsibility within it).
- **Condition**: one input/state combination that changes the outcome
  (branches, edge cases, error paths all count).
- **ExpectedResult**: the observable outcome for that Condition — read off
  the actual code (return value, error, side effect), never guessed.

Do not invent behavior the code doesn't show. If intent is ambiguous (e.g. a
`TODO`, or two plausible readings of a branch), stop and ask the user rather
than guessing.

### Phase 3 — Check axes

1. Run `markharness axes list --json` to see the registered `axes/*.yml`
   entries.
2. Every `axis` value you plan to use on a _new_ requirement/feature/behavior
   must already be registered (`markharness knowledge validate` rejects
   unknown axes with `unknown_axis`, with a nearest-match suggestion). If a
   needed axis doesn't exist, create `axes/<id>.yml` with `id:`/`label:`
   fields before continuing — `markharness` has no `axes add` subcommand.

### Phase 4 — Draft, validate, apply (repeat per Condition)

For each Condition identified in Phase 2:

1. Write a draft YAML file (e.g. to a scratch path) matching the
   `KnowledgeDraft` schema. A blank template is available via
   `markharness knowledge scaffold` (prints to stdout, or writes to a file
   with `--out <path>` — it refuses to overwrite an existing file). A
   reference schema for editor/IDE autocompletion is also available at
   `docs/knowledge_draft.schema.json` (reference only — state-dependent
   rules such as "label/axis/description are optional once the entry
   already exists" or "axis values must already be registered under
   `axes/`" can't be expressed in plain JSON Schema, so the real checks are
   always performed by `knowledge validate`/`apply`):

   ```yaml
   requirement:
     id: <existing-or-new-requirement-slug>
     label: <label> # omit if requirement already exists and unchanged
     axis: [<axis-id>, ...]
     description: <text or null>

   feature:
     id: <feature-slug>
     label: <label>
     axis: [<axis-id>, ...]
     description: <text>
     # forked_from: <existing-feature-id>   # only when genuinely a variant of another Feature

   behavior:
     id: <behavior-slug>
     label: <label>
     axis: [<axis-id>, ...]
     description: <what this Behavior does, in the code's own terms>

   condition:
     id:
       <condition-slug> # do not repeat the behavior id as a prefix
       # MUST be unique across the entire knowledge/
       # tree, not just within its Behavior — see
       # "Condition id collisions" below
     label: <label>
     description: <the specific input/state that triggers this path — cite file:line>

   expected:
     - description: <observable outcome, read from the code — cite file:line>
   ```

   Omit `label`/`axis`/`description` on any level that already exists and is
   unchanged — supplying a conflicting value fails validation with
   `conflicting_existing_value`.

   **Condition id uniqueness:** `markharness generate` writes each Condition
   to `generated/testcases/<requirement>/<feature>/<behavior>/<condition-id>.yml`
   — it fully mirrors `knowledge/`'s own hierarchy. So `condition.id` only
   needs to be unique within its own Behavior (`markharness knowledge
   validate`/`apply` enforce exactly that scope), and reusing the same id
   under a different Behavior (e.g. `valid-title` under both `add-todo` and
   `edit-todo`) never collides in the generated output. No renaming or
   collision-avoidance work is needed — see "Principles" below for details.

2. Validate: `markharness knowledge validate <draft-file> --json`. Fix every
   reported error (`invalid_slug`, `missing_axis`, `missing_description`,
   `unknown_axis`, `redundant_prefix`, `conflicting_existing_value`,
   `parent_not_found`, `unknown_forked_from`) before proceeding.
3. Apply: `markharness knowledge apply <draft-file> --json` (add
   `--strip-redundant-prefix` only if you intentionally want a
   `behavior-`-prefixed `condition.id` stripped).
4. Mark the corresponding checklist step done.

To process multiple Conditions at once, collect the draft files in a single
directory and batch-validate them with `markharness knowledge validate
--batch <dir> --json` (or `markharness knowledge apply --batch <dir>
--dry-run --json`, which runs the same check) before running `markharness
knowledge apply --batch <dir> --json`. Files are applied in filename order
within the directory, and a later draft in the batch may reference a
Requirement/Feature/Behavior an earlier draft in the same batch just
created. If `apply --batch` (without `--dry-run`) fails partway through, the
entire call is rolled back, including files it had already written in that
same invocation — a batch apply is all-or-nothing.

### Phase 5 — Generate

Once every planned Condition has been applied:

1. Run `markharness generate` to deterministically (re)write
   `generated/testcases/*.yml` from `knowledge/`.
2. Confirm the count of generated files matches the count of Conditions
   applied (e.g. `find knowledge -name condition.yml | wc -l` vs. `find
generated/testcases -type f -name "*.yml" | wc -l` — note no `-maxdepth 1`:
   `generated/testcases/` mirrors `knowledge/`'s hierarchy, so files are
   nested, not flat). A mismatch suggests an unintended duplicate, e.g. the
   same requirement/feature/behavior/condition combination applied more than
   once — investigate before regenerating.
3. Run `markharness validate` to confirm `knowledge/`/`axes/` still conform
   to `schema/*.schema.json` and cross-references resolve.
4. Re-run `markharness generate` once more and confirm no diff — this is
   what most CI setups check, so verify it locally before handing off.

### Phase 6 — Wrap up

1. Add a `## Summary` section to the checklist file: which
   Feature/Behavior/Condition were added, and which code (file:line) each
   traces back to.
2. Report to the user which `generated/testcases/*.yml` files are
   new/changed, and flag anything you had to skip because the code's intent
   was ambiguous.

## Principles

- Every Condition/ExpectedResult must cite the code it came from — no
  speculative test knowledge.
- Never hand-edit `generated/testcases/*.yml`; it is derived output. Only
  write under `knowledge/` (via `apply`) and let `markharness generate`
  produce the rest.
- Prefer many small drafts (one per Condition) over one giant draft — easier
  to validate and fix incrementally.
- If a Condition's outcome depends on external state the code doesn't fully
  determine (I/O, concurrency, config), say so in the description rather
  than asserting a single deterministic outcome.
- `condition.id` only needs to be unique within its Behavior (`knowledge
  apply`/`knowledge validate` enforce this). `generate`'s output fully
  mirrors `knowledge/`'s own hierarchy
  (`generated/testcases/<requirement>/<feature>/<behavior>/<condition>.yml`),
  so reusing the same `condition.id` under a different Behavior no longer
  collides (the earlier flat `generated/testcases/<condition-id>.yml`
  layout silently overwrote on such a collision; this has since been
  structurally fixed).
