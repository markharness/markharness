# Knowledge From Code (standalone)

> This file is self-contained — copy it alone into any project (or paste its
> body directly into a chat with an AI coding assistant) and it works without
> any other file from the `markharness` template repo. The only external
> requirement is the `markharness` CLI itself (see Phase 0).
>
> Respond in the language the user is using in the chat.

You will read existing source code and derive `markharness` test knowledge
from it, then generate `TestCase` data with `markharness generate`. This is
AI-assisted authoring of test knowledge
(`.markharness/knowledge/**/{requirement,feature,behavior,scenario}.yml`), not
a replacement for human review: every derived Scenario/Phase must be
traceable to a specific place in the code.

## Progress tracking (inline checklist rules)

Before starting, create `checklist-knowledge-from-code.md` in the project
root:

```markdown
# Task: Derive knowledge/ from <target code>

Created: <date>

## Steps

- [ ] <one line per Behavior you plan to extract>

## Notes

<context, decisions, blockers>
```

- Mark a step `- [x]` immediately after finishing it, not in a batch later.
- If a step turns out unnecessary, mark it `- [~] Skipped: <reason>` instead
  of deleting it.
- When every step is done, add a `## Summary` section (see Phase 7).

## Data model (for reference — no other file needed)

Feature is a **top-level** directory keyed by its own id under `features/`,
not a subdirectory nested under a Requirement. The relationship to a
Requirement is carried by the Feature's own `requirement_uids` (plural), so
one Feature may relate to several Requirements as equals. See
`docs/en/decisions/0017-scenario-case-revision-and-execution-evidence.md` for
the full rationale.

```text
.markharness/
├── knowledge/
│   ├── requirements/
│   │   └── <requirement>/
│   │       └── requirement.yml
│   └── features/
│       └── <feature>/           # top-level, not nested under a Requirement
│           ├── feature.yml      # requirement_uids: [<requirement's uid>, ...]
│           └── <behavior>/
│               ├── behavior.yml # procedures: named shared step sequences (optional)
│               └── <scenario>/
│                   └── scenario.yml  # phases: an ordered array of steps (action/use) and results
├── axes/                # cross-cutting axis registry, one axes/<id>.yml per axis
├── schema/               # default schema files created by markharness init
└── generated/
    └── testcases/        # <feature>/<behavior>/<scenario>.yml, deterministically regenerated by `markharness generate` — never hand-edit
```

There is no Condition/ExpectedResult split anymore. A Scenario's ordered
`phases` array (each phase carrying its own `steps` and `results`) replaces
it, and **1 Scenario = 1 TestCase**. Execution order is the phases array
order itself, never filename order.

## Procedure

### Phase 0 — Confirm the tool is available

1. Run `markharness --version` (or `--help`). If the command is not found,
   stop and tell the user: they need to build/install `markharness` first
   (from its repo: `cargo install --path .`, or use a prebuilt binary), or
   confirm they actually meant a different tool. Do not attempt to fabricate
   its output or proceed without it.
2. Check whether the target directory already has `.markharness/` (with
   `knowledge/`, `axes/`, `schema/`, etc. inside it) — i.e. `markharness init`
   has run there. If it doesn't, run `markharness init --dir <target>` first
   — it creates `.markharness/{knowledge,axes,generated,executions,changes,schema}`
   plus the default `.markharness/schema/*.schema.json` files that
   `markharness validate` needs, and the project-root marker
   `.markharness/config.toml`, without touching anything that already exists.
3. Once a project has been `init`ed (an ancestor directory has
   `.markharness/config.toml`), every subsequent command auto-detects the
   project root by walking up from the current directory, so `--dir` can be
   omitted. Pass `--dir <target>` explicitly when working across multiple
   projects at once, or when the current directory is outside the project.
4. On a brand-new project, `axes/` will be empty, so _every_ axis you plan to
   use must be created (Phase 3) before drafting — there is no pre-existing
   registry to fall back on.

### Phase 1 — Scope

1. Identify the target code (file/module/function the user pointed at, or
   ask if unclear).
2. Confirm the `requirement` this code belongs to (an existing
   `.markharness/knowledge/requirements/<requirement>/` id, or a new one to
   create — on a fresh project this is always new).
3. Fill in the checklist file created above with one step per Behavior you
   plan to extract.

### Phase 2 — Analyze code

For the target code, read it and identify, per public function/branch/error
path:

- **Feature**: the user-facing capability the code implements. Relates to one
  or more Requirements via `requirement_uids` (see "migrate the Requirement
  first" in Phase 4).
- **Behavior**: one distinct thing the Feature does (e.g. one function, or
  one responsibility within it). If several Scenarios share an operation
  sequence, declare it here as a named `procedures` entry.
- **Scenario**: one per input/state combination that changes the outcome
  (branches, edge cases, error paths all count). Carries an ordered `phases`
  array, each phase pairing an operation sequence (`steps`) with the outcome
  observable after it (`results`). **1 Scenario = 1 TestCase.**

Do not invent behavior the code doesn't show. If intent is ambiguous (e.g. a
`TODO`, or two plausible readings of a branch), stop and ask the user rather
than guessing.

Always keep in mind that `phases[].steps` is a script a human Test Executor
reads and carries out by hand — markharness has no auto-execution engine.
It's fine to read the code to back up each operation, but write the operation
itself as something a human (or an equivalent manual operator) can actually
perform — a screen click, a form input, sending an API request — never a
function call or internal processing step. Write "type 'Buy milk' into the
input field, then click the Add button", not "call `addTodo()`". Each
`steps` element is either `action: <operation>` or
`use: <a procedure name the Behavior declares>`.

Multiple independent observations after the same operation go into one
phase's `results` as multiple lines; create a new phase only for a genuinely
new operation (`steps` not present in the prior phase) that must happen
before the next outcome can be observed.

When citing provenance in a `description` as "file path + function/method
name", watch out for a YAML trap: **a colon immediately followed by a space
inside a plain scalar is parsed as a mapping separator**, so
`description: added (app.js: addTodo)` fails to parse. Separate the file
path and function name with something other than a colon+space — e.g.
`app.js#addTodo` or `app.js > addTodo` — or wrap the whole value in double
quotes (`description: "added (app.js: addTodo)"`).

### Phase 3 — Check axes

1. Run `markharness axes list --json` to see the registered
   `.markharness/axes/*.yml` entries.
2. Every `axis` value you plan to use on a _new_ requirement/feature/behavior
   must already be registered (`markharness knowledge validate` rejects
   unknown axes with `unknown_axis`, with a nearest-match suggestion). If a
   needed axis doesn't exist, register it first with
   `markharness axes add <id> [--label <label>]` (omitting `--label` uses
   `id` as the label; an id that already exists is an error).
3. A Scenario has no axis of its own — a generated TestCase's `axis` is the
   union (deduplicated, sorted) of its Feature's and Behavior's axis.
   Requirement axis is never inherited automatically (cross-cutting search by
   Requirement is meant to follow the `requirement_ids`/`requirement_uids`
   relationship instead).

### Phase 4 — Migrate the Requirement's identity (new Requirements only)

A Feature relates to a Requirement by the Requirement's immutable uid, not
its display id. **A brand-new Requirement has no uid until
`markharness identity migrate` runs**, and until then any new Feature trying
to reference it is rejected with `requirement_not_migrated`.

1. If you're only reusing an existing Requirement (not creating one), skip
   this phase and go straight to Phase 5.
2. When creating a new Requirement, run `markharness knowledge add`
   (interactive mode) and enter the Requirement's name (and axis). A
   brand-new Requirement always has no uid until `identity migrate` runs, so
   the interactive session stops right after writing the Requirement and
   never goes on to prompt for a Feature. **`markharness knowledge apply`
   (draft file) has no way to write a standalone Requirement** — a draft
   always requires all four sections (requirement/feature/behavior/scenario),
   so attempting to create a brand-new Requirement and a brand-new Feature in
   the same draft is always rejected at validation time with
   `requirement_not_migrated`, and nothing gets written (this combination is
   structurally impossible by design).
3. After creating the Requirement, run
   `markharness identity migrate --dir <target>`. This is an idempotent
   operation: it assigns a uid to every Knowledge element
   (Requirement/Feature/Behavior/Scenario) that doesn't have one yet, and
   does nothing to elements that already do. Add `--dry-run` to preview the
   planned assignments without writing anything, and `--json` for
   machine-readable output.
4. Before applying a draft that creates a new Feature, confirm the
   Requirement(s) it references have already been migrated.

### Phase 5 — Draft, validate, apply (repeat per Scenario)

For each Scenario identified in Phase 2:

1. Write a draft YAML file (e.g. to a scratch path) matching the
   `KnowledgeDraft` schema. A blank template is available via
   `markharness knowledge scaffold` (prints to stdout, or writes to a file
   with `--out <path>` — it refuses to overwrite an existing file):

   ```yaml
   requirement:
     id: <existing-or-new-requirement-slug>
     label: <label> # omit if requirement already exists and unchanged
     axis: [<axis-id>, ...]
     description: <text or null>

   feature:
     id: <feature-slug>
     label: <label>
     axis: [<axis-id>, ...]
     description: <text>
     # forked_from: <existing-feature-id>   # only when genuinely a variant of another Feature

   behavior:
     id: <behavior-slug>
     label: <label>
     axis: [<axis-id>, ...]
     description: <what this Behavior does, in the code's own terms>
     procedures: # optional (omitted means "no procedures"). Also omit entirely when reusing an existing Behavior unchanged
       - name: <procedure-slug> # referenced from this Behavior's own scenario.phases via `use: <name>`
         steps:
           - <this procedure's own operation sequence, written as something a human can do by hand; at least 1 required>

   scenario:
     id:
       <scenario-slug> # do not repeat the behavior id as a prefix
       # only needs to be unique within this Behavior —
       # see "Scenario id uniqueness" below
     label: <label>
     description: <the specific input/state that triggers this path — cite the file path and function/method name (never a line number, see "Principles")>
     phases: # always fully specified (unlike Requirement/Feature/Behavior, a Scenario has no "omit if unchanged" shortcut) — at least 1 required
       - steps:
           - action: <something a human can do by hand> # or `- use: <procedure-slug>`
         results:
           - <the observable outcome after this phase's operation, read from the code; one element = one observation; at least 1 required>
     implementation_note: <implementation rationale note; optional; not used for generation>
   ```

   Omit `label`/`axis`/`description`/`procedures` on a Requirement/Feature/
   Behavior that already exists and is unchanged — supplying a conflicting
   value fails validation with `conflicting_existing_value`. A Scenario has
   no such "omit to reuse" shortcut — `description`/`phases` are always
   fully specified, and reusing an existing `scenario.id` is checked for an
   exact content match (a mismatch is `conflicting_existing_value`).

   To verify multiple phases under the same Scenario (e.g. "check right
   after adding" then "check persistence after a reload"), write multiple
   entries in the `phases` array. Create a new phase only for one that
   introduces a genuinely new operation (`steps` not present in the prior
   phase) — if you just want to split one operation's outcome across
   multiple lines, add lines to the existing `results` instead of creating a
   new phase.

   **Scenario id uniqueness:** `markharness generate` writes each Scenario to
   `.markharness/generated/testcases/<feature>/<behavior>/<scenario-id>.yml` — it fully
   mirrors `.markharness/knowledge/features/`'s own hierarchy (Feature at the
   top level). So `scenario.id` only needs to be unique within its own
   Behavior (`markharness knowledge validate`/`apply` enforce exactly that
   scope), and reusing the same id under a different Behavior (e.g.
   `valid-title` under both `add-todo` and `edit-todo`) never collides in the
   generated output. No renaming or collision-avoidance work is needed — see
   "Principles" below for details.

2. Validate: `markharness knowledge validate <draft-file> --json`. Fix every
   reported error (`invalid_slug`, `missing_axis`, `missing_description`,
   `missing_steps`, `unknown_axis`, `redundant_prefix`,
   `conflicting_existing_value`, `parent_not_found`, `unknown_forked_from`,
   `multiline_label`, `requirement_not_migrated`) before proceeding.
   `requirement_not_migrated` means Phase 4 hasn't been done yet — run
   `markharness identity migrate` first. `missing_steps` fires when any of
   `behavior.procedures[].steps`/`scenario.phases`/`scenario.phases[].steps`/
   `scenario.phases[].results` is missing/empty, or contains a
   blank/whitespace-only element. `behavior.procedures[].steps` is rejected
   outright when empty on a new procedure, and `scenario.phases` and its
   `steps`/`results` are always required non-empty — even when reusing an
   existing Scenario — unlike the old model's `additional_preconditions`/
   `additional_steps`, which allowed an empty array `[]`; that exception no
   longer exists.
3. Apply: `markharness knowledge apply <draft-file> --json` (add
   `--strip-redundant-prefix` only if you intentionally want a
   `behavior-`-prefixed `scenario.id` stripped).
4. Mark the corresponding checklist step done.

To process multiple Scenarios at once, collect the draft files in a single
directory and batch-validate them with `markharness knowledge validate
--batch <dir> --json` (or `markharness knowledge apply --batch <dir>
--dry-run --json`, which runs the same check) before running `markharness
knowledge apply --batch <dir> --json`. `--batch <dir>` only picks up direct
`*.yml` children (`.yaml`-suffixed files are ignored, and it exits with code
2 if none are found). Files are applied in filename order within the
directory, and a later draft in the batch may reference a
Requirement/Feature/Behavior an earlier draft in the same batch just created
(e.g. name them `01-xxx.yml`, `02-xxx.yml` to control order). If
`apply --batch` (without `--dry-run`) fails partway through, the entire call
is rolled back, including files it had already written in that same
invocation — a batch apply is all-or-nothing.

### Phase 6 — Generate

Once every planned Scenario has been applied:

1. Run `markharness generate` to deterministically (re)write
   `.markharness/generated/testcases/*.yml` from `.markharness/knowledge/`. The
   granularity is 1 Scenario = 1 TestCase; each file is composed of
   `generated_from` (the feature/behavior/scenario provenance, plus the
   `requirement_ids`/`requirement_uids` relationship), `phases` (copied from
   `scenario.yml`'s `phases`, with any `use:` reference already expanded to
   its Behavior's procedure steps), and `axis` (the union of Feature's and
   Behavior's axis).
2. Confirm the count of generated files matches the count of Scenarios
   applied (e.g. `find .markharness/knowledge/features -name scenario.yml |
   wc -l` vs. `find .markharness/generated/testcases -type f -name "*.yml" | wc -l` —
   note no `-maxdepth 1`: `.markharness/generated/testcases/` mirrors
   `.markharness/knowledge/features/`'s hierarchy, so files are nested, not
   flat). A mismatch suggests an unintended duplicate, e.g. the same
   feature/behavior/scenario combination applied more than once — investigate
   before regenerating.
3. Run `markharness validate` to confirm `.markharness/knowledge/`/
   `.markharness/axes/` still conform to `.markharness/schema/*.schema.json`
   and cross-references resolve.
4. Re-run `markharness generate` once more and confirm no diff — this is
   what most CI setups check, so verify it locally before handing off.

### Phase 7 — Wrap up

1. Add a `## Summary` section to the checklist file: which
   Feature/Behavior/Scenario were added, and which code (file path,
   function/method name — no line numbers, see "Principles") each traces
   back to.
2. Report to the user which `.markharness/generated/testcases/*.yml` files are
   new/changed, and flag anything you had to skip because the code's intent
   was ambiguous.

## Principles

- Every Scenario/Phase must cite the code it came from — no speculative test
  knowledge. Keep the citation to "file path + function/method/branch name"
  only — a line number drifts on every unrelated refactor, so recording it
  only adds upkeep cost to `knowledge/` without improving verifiability.
- Write `phases[].steps` (`action:` or `use:`) as operations a human Test
  Executor can carry out by hand (screen interactions, input, sending an API
  request), backed by reading the code but never expressed as function names
  or internal processing. markharness has no auto-execution engine — these
  are a script a human reads top to bottom and performs.
- Never hand-edit `.markharness/generated/testcases/*.yml`; it is derived output. Only
  write under `.markharness/knowledge/` (via `apply`) and let
  `markharness generate` produce the rest.
- Prefer many small drafts (one per Scenario) over one giant draft — easier
  to validate and fix incrementally.
- If a Scenario's outcome depends on external state the code doesn't fully
  determine (I/O, concurrency, config), say so in the description rather
  than asserting a single deterministic outcome.
- The order of the `scenario.phases` array is not cosmetic — it is the
  contract that determines the execution order of the generated TestCase's
  `phases` (the old model used filename order; array order is now the sole
  authority). Reordering it changes the test's meaning. Multiple
  observations after the same operation belong in one phase's `results`;
  create a new phase only for one that introduces a genuinely new operation.
- `scenario.id` only needs to be unique within its Behavior (`knowledge
  apply`/`knowledge validate` enforce this). `generate`'s output fully
  mirrors `.markharness/knowledge/features/`'s own hierarchy
  (`.markharness/generated/testcases/<feature>/<behavior>/<scenario>.yml`, Feature at the
  top level), so reusing the same `scenario.id` under a different Behavior
  never collides.
- A newly created Requirement can't be referenced by a Feature yet — until
  `markharness identity migrate` assigns it a uid, it's rejected with
  `requirement_not_migrated` (see Phase 4). This migrate step is idempotent,
  so running it repeatedly is harmless.
