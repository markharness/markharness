# 0041: `coverage`で、bindingの参照先が実在するかを示す

## ステータス

Accepted(2026-10-05決定)。

## 背景

GUIのRelease Coverage視点は、`coverage`の`case_coverage`にある`binding_mode`と`binding_reference`から、各ケースの検証手段を示す。レビューの目的の1つは、テスト実装との対応が解決していないものを見つけることである。しかし`binding_reference`は、`ExecutionBinding`に書かれた自由文字列をそのまま返すだけで、参照先があるかどうかを確かめていない。参照先が消えている、またはタイプミスの場合でも、GUIは「自動(参照)」と示してしまい、実在しない参照を実在するものと取り違えさせる(Issue #98)。

実在するかどうかは、リポジトリの構造に関する事実であり、実行結果ではない。[0025](./0025-v2-forward-compatible-evolution.md)§1が禁じているのは、bindingの存在を「実行済み」「合格」と読むことである。参照先の有無を示すことは、この線を越えない。

## 決定

### 1. `case_coverage`に`reference_status`を加える

`binding_reference`がある場合に限り、その隣に`reference_status`を返す。値は3つである。

| 値 | 意味 |
|---|---|
| `exists` | 参照が、`--at`で指定したコミットのGit treeにあるパスと一致する |
| `missing` | 一致しない。または絶対パス・`..`を含むパス・空文字で、リポジトリの外を指しうる |
| `not_checked` | 参照がURLである。到達性は確認しない |

`binding_reference`がない場合(bindingがない、または`reference`が未宣言)は、`reference_status`も省略する。「参照がない」と「参照が確認の対象外」は、GUIで別の意味を持つため、混ぜない。

`exists`は「参照先がある」ことだけを言い、そのテストが実行されたことも、合格したことも言わない([0025](./0025-v2-forward-compatible-evolution.md)§1)。

### 2. 判定は`--at`のコミット時点のtreeで行う

作業ツリーのファイルは見ない。GUIは過去のコミットも読むため、作業ツリーで判定すると、過去の表示を今日の状態で誤らせる。Knowledge・選定リスト・bindingがすべて`--at`のコミットから読まれる既存の規則([設計書](../design/cli-read-model-design.md)P3)と揃える。コミットされていないファイルは、そのコミットには存在しない。

### 3. 参照の形の判別

- `://`を含む文字列はURLとみなし、`not_checked`にする。
- それ以外は、`--dir`のプロジェクトルートからの相対パスとして、`git ls-tree`で`--at`のコミットのtreeに問い合わせる。ファイルでもディレクトリでも、treeにその名前そのままの項目があれば`exists`にする(末尾に`/`を付けたディレクトリ名は一致しない)。手動ケースが資料のフォルダを指す場合があるためである。
- ルート相対とは、`--dir`で指定したディレクトリを基準とする。`--dir`がGitリポジトリのサブディレクトリの場合も、`git ls-tree`のpathspecが`-C`相対で解決されるので、同じ基準になる。

### 4. 誤判定されうるパターンを、仕様として明記する

`reference`は自由文字列で、種別を持たない。判別規則を単純に保つ代わりに、次の場合に実態とずれた値を返す。これは欠陥ではなく、この決定の範囲である。

- **シンボルや行番号の接尾辞。** `tests/a.spec.ts::jumps`や`tests/a.spec.ts#L10`のように、パスの後ろに付いた部分は切り落とさない。文字列全体を1つのパスとして判定するため、実在するファイルを指していても`missing`になる。
- **バックスラッシュ区切り。** `tests\a.spec.ts`は変換しないので、`missing`になる。
- **正規化・展開の不使用。** 参照はGitのpathspecではなく、文字列そのままの完全一致で判定する。`./tests/a.spec.ts`、`tests//a.spec.ts`、末尾が`/`の`tests/`、`tests/*.spec.ts`のようなワイルドカード、`:(top)`のようなpathspec構文は、いずれも解釈・正規化・展開せず、`missing`になる。`[a].ts`のように`[`や`*`を含む実在のファイル名は、その名前だけに一致する。
- **`://`を含むパス。** 実在するパスに`://`が含まれていても、URLとみなして`not_checked`にする。
- **URLの実在。** `not_checked`は、URLが有効かどうかを何も示さない。

`missing`は「`--at`のコミットのtreeに、その文字列のパスが無い」という意味であり、「参照が間違っている」とは限らない。

## 理由

- レビューの目的に直結し、viewが自前で判定する手段もない(viewは`.markharness/`やGitを直接読まない。[0040](./0040-traceability-show-element-detail.md))。
- 判定は`git ls-tree`1回で済み、新しい依存を要さない。
- 3値だけで、Issueの要求(実在する・しない・確認対象外の区別)を満たす。
- 接尾辞の切り落としなどの規則は、実際に使われる形式が確認できていない。確認前に規則を足すことは、現時点で要求されていない汎用化である。誤判定は、仕様として明記して許容する。

## 検討した代替案

- **作業ツリーで判定する。** 過去のコミットを`--at`で読むと、今日のファイルの有無で結果が変わる。再現性を損なうので採用しない。
- **`reference`に種別(`path`・`url`)を持たせる。** `ExecutionBinding`の形式が変わる。今回の要求は3値の区別だけで足りるので採用しない。
- **`::`と`#`以降を切り落としてから判定する。** 使われる書き方が確認できていない。誤った規則を固定するより、まず接尾辞付きの参照が`missing`になることを許容し、実例が出てから決める。採用しない。
- **URLの到達性を確認する。** ネットワークに依存し、再現性を損なう。Issueでも不要とされている。採用しない。
- **`binding list --json`にも同じ項目を付ける。** GUIは使わない。採用しない。

## 帰結

- `schema/release-coverage-read-model.schema.json`と、`tests/fixtures/read-models/release_coverage/v1/representative.json`に`reference_status`を加える。項目の追加だけで、既存の項目の意味は変わらないので、`rule_version`と`schema_version`は上げない([0039](./0039-read-output-schema-version-frozen-in-prototype.md))。
