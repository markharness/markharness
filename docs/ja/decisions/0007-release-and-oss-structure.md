## コンテキスト

markharness は現在、以下の状態で公開されている。

- 公開リポジトリ `markharness/markharness` と、開発リポジトリ(本リポジトリ、テンプレート由来の `.github/` / `PROJECT.md` / `docs/decisions/` / `tests/` / `examples/` を含むフルセット)が分離されている。
- 公開リポジトリの `Cargo.toml` は `version = "0.1.0"`(SemVer)だが、gitタグは `v2026.08.13`(CalVer)であり、バージョン識別子が2種類併存している。
- 公開リポジトリ・開発リポジトリのいずれにも `.github/workflows/` が存在せず、CI・リリースの自動化が無い。
- 依存クレート `kakasi 0.1.0` が GPL-3.0 ライセンスであり、プロジェクト全体が宣言する MIT ライセンスと矛盾している(静的リンクにより combined work となるため)。
- `markharness.com` は GitHub Pages が README.md をそのまま自動レンダリングしたものであり、追加のビルド設定は無い。
- GitHub Wiki は未作成(存在確認不可、推測含む)。
- 開発リポジトリの `docs/` には、公開リポジトリに存在しない多数のドキュメント(`cli-manual.md`、`product-operation.md`、`testcase-generation-design.md` 等)がある。

これらを踏まえ、リリース工程とOSSとしての公開構造を、後方互換性を考慮せず最善の形に再設計する。

## 決定

### 1. リポジトリ構成: 単一リポジトリへ統合する

現在の二リポジトリ構成を廃止し、開発・公開を単一リポジトリで行う。

理由:

- 公開リポジトリのコミット履歴がキュレーション目的のコミット(`Create CNAME` 等)のみで構成されており、実装の経緯を `git blame` で追跡できない。外部コントリビュータのコード理解を妨げている。
- 手動同期に起因するドリフトが既に発生している(Cargo.toml と git タグのバージョン不整合)。
- 公開リポジトリに `tests/` / `examples/` が存在せず、外部コントリビュータが開発リポジトリ側の資産にアクセスできない。PR提出先が実質的に存在しない。
- `PROJECT.md` / `CLAUDE.md` / `.claude/` 等の内部運用ファイルは、認証情報等の機密を含まないため(確認済み)、公開する実害がない。単一リポジトリに統合すること自体を妨げる理由ではないが、実際にどこまで公開するか(追跡対象に含めるか)は別途「ステータス」欄の通り、最低限の公開フットプリント方針により追跡除外に変更した。

運用ルール:

- `main` ブランチで開発を継続する。CIが通らないコミットはマージしない。
- バイナリのリリース物は `v*` タグのpushを契機にのみ生成する(第4節)。ただしPages(`markharness.com`)は現状どおりmainブランチのREADME.mdを都度自動レンダリングする設定を維持するため(第5節)、Docsサイトの更新はタグ契機ではなくmainへのpush毎に即時反映される。両者は生成契機が異なる別物であると明確に区別する。未成熟な変更が利用者の目に触れうるのはこのPages経由のREADME/docsのみであり、バイナリ配布物についてはタグを打った時点のスナップショットが常に安定している。
- ADRは番号・ディレクトリを`docs/decisions/`単一に固定し、確定していない/一部未実行の文書もここに置く。ライフサイクル(Proposed / Accepted / Rejected / Deprecated / Superseded、および実行途中を表す`Accepted(一部実行済み)`等の項目固有の追記)は各ファイル冒頭の`## ステータス`セクションで表現し、状態が変わってもファイルを別ディレクトリへ移動しない(Michael Nygard「Documenting Architecture Decisions」・MADRの運用に準拠。理由は「番号空間の分断」「移動に伴うリンク陳腐化」を参照)。OSS公開時に非公開としたい個別ファイル(例: 却下判定のみで製品判断に寄与しない作業メモ)は、ディレクトリ分離ではなく第7節の`git filter-repo`でファイル単位に除去する。
- `docs/template-readme.md` のような、製品と直接関係しない/恒久性のない文書は削除またはアーカイブする。`docs/gap-analysis-mh-sample-test-case.md` は当初この対象に含めていたが、README.md・論文本体・`design/change-event-verification-tracking-spec.md` から監査ログとして現役参照されているため対象外とし、維持する。

### 2. ライセンス: 依存関係の整合を最優先で是正する

`kakasi`(GPL-3.0)をMIT/Apache-2.0互換の代替に置き換える、または該当機能を自前実装する。これをリリース自動化より優先して着手する。放置した場合、MITライセンスを掲げたバイナリ配布がライセンス条件を満たさない状態が継続する。

是正後、`cargo-deny` の `licenses` チェックをCIに組み込み、許可ライセンス一覧(MIT, Apache-2.0, BSD系等)に無い依存が混入した時点でCIを失敗させる。

### 3. バージョニング: SemVerに一本化する

CalVerタグ(`v2026.08.13`)運用をやめ、`Cargo.toml` の `version` フィールドと git タグ(`vX.Y.Z`)を単一の情報源として一致させる。

- 0.x系を継続し、UC8(既存TMSインポータ)実装・スキーマ安定化を1.0への基準とする。
- タグは常に `Cargo.toml` の `version` と一致させる。CIで「タグ名とCargo.tomlのversionが一致しているか」を検証するステップを設け、不一致ならリリースジョブを失敗させる。

### 4. CI: PRゲートとリリースパイプラインを分離する

**PRゲート(push/PR契機)**

- `cargo test`
- `cargo clippy --all-targets -- -D warnings`
- `cargo fmt --check`
- `cargo audit`(脆弱性)
- `cargo deny check licenses`(ライセンス整合、今回のkakasi問題の再発防止)
- `markharness verify`(`generated/testcases/*.yml` と `knowledge/` の一致確認)

既存のPre-PRチェックリスト(手動運用)をそのままCIのジョブ定義に落とし込む。

**リリースパイプライン(`v*` タグpush契機)**

1. タグ名と `Cargo.toml` の `version` の一致を検証。
2. クロスプラットフォームビルド(`x86_64-pc-windows-msvc`、`x86_64-unknown-linux-gnu`、`x86_64-apple-darwin`、`aarch64-apple-darwin`)。当初`cargo-dist`の採用を想定していたが、依存追加を避けるため標準の`actions/upload-artifact`等を使った手組みのmatrix buildで実装した。`x86_64-pc-windows-gnu`は需要が確認できなかったため対象から外した(必要になれば追加する)。
3. チェックサム(SHA256SUMS)生成。インストーラスクリプトは現時点では生成しない(未実装、必要になれば追加する)。
4. GitHub Releasesへ添付。Conventional CommitsからのCHANGELOG自動生成(`git-cliff`)をリリースノートとして添付。
5. (任意)`cargo publish` による crates.io 公開。ライブラリとしての利用を想定しない限り必須ではない。未実装。

## 結果

- リポジトリが単一になることで、Issue/PR/コミット履歴が一箇所に集約され、外部コントリビュータの参入障壁が下がる。
- ライセンス矛盾の解消により、配布物の法的整合性が確保される。
- バージョニングとリリースの自動化により、手動運用に起因するドリフト(今回発見したバージョン不整合)が構造的に再発しなくなる。
- Wiki不採用・Pages現状維持により、文書の「正」の所在が `docs/` に一本化される。

## 7. 既存公開リポジトリの削除・再作成

前提として、既存の公開リポジトリ `markharness/markharness` を削除し、新規に作り直すことを許容する。単純に「既存リポジトリを整形する」のではなく削除・再作成を選ぶ理由は以下の通り。

- 既存の公開リポジトリのコミット履歴はキュレーション目的のコミット(`Create CNAME` 等)のみで構成されており、実質的な価値が無い。これを土台に整形するより、価値のある履歴(開発リポジトリの実履歴)を土台にする方が、後から履歴を継ぎ足すよりクリーンに達成できる。
- CalVerタグ(`v2026.08.13`)とSemVer(`Cargo.toml` の `0.1.0`)の混在を、後方互換を気にせず一度に解消できる。既存タグを打ち直す(force update)よりも、新規リポジトリで最初から正しいタグ体系を使う方が事故が少ない。
- kakasi(GPL-3.0)問題を是正した状態を「最初のコミット」にできる。既存リポジトリの履歴には、ライセンス上問題のある依存を含んだバイナリが既にリリースされていた事実が残り続けるが、これは新規リポジトリでは回避できる(ただし旧リポジトリのRelease配布物自体が既に外部にダウンロードされている可能性は消せない。この点は後述)。

### 実行順序

削除は最後に行う。以下の順で準備を完了させてから削除・再作成する。

1. **開発リポジトリ内でkakasi問題を是正**(第2節)。この時点でCargo.tomlのライセンス表記と実態が一致する状態にする。
2. **開発リポジトリの履歴から非公開パスを除去したクリーンな履歴を作る**。`git filter-repo`(BFGではなくfilter-repoを推奨。履歴書き換えの柔軟性が高く、GitHub公式も推奨している)で、`docs/template-readme.md`、`CLAUDE.md`、`PROJECT.md`、`.claude/`、`.github/copilot-instructions.md`、`.github/instructions/`、`.github/prompts/`、`.github/skills/`、`checklist-*.md`(最低限の公開フットプリント方針、ステータス欄参照)等、公開に適さないパスを履歴ごと除去する。`docs/gap-analysis-mh-sample-test-case.md`は監査ログとして現役参照されているため除去対象に含めない。`docs/decisions/`配下のADR(0001〜0007)はいずれも`Status: Accepted`であり除去対象に含めない(第5節)。これにより、単なる最新スナップショットのコピーではなく、**実際の開発の経緯を保持したまま**公開できる(第1節で述べた「履歴の透明性」というOSSの利点を、フルヒストリーの形で獲得できる)。
3. **タグを再構成**。既存のCalVerタグは使わず、SemVerで `v0.1.0` から採番し直す(あるいは、これまでの開発の蓄積を踏まえて `v0.2.0` 等、実態に即したバージョンから開始してもよい)。
4. **CI/CDをこの時点で組み込む**。新規リポジトリの最初のコミットからPRゲートCIとリリースパイプライン(第4節)が機能する状態にする。「後から追加する」のではなく「最初から備わっている」状態を作れるのは、作り直す場合の明確な利点。
5. **ガバナンスファイル(第6節)を追加**した状態を初期コミット群に含める。
6. 既存の `markharness/markharness` を削除する。
7. 同名でリポジトリを新規作成し、フィルタ済み履歴をpushする。
8. GitHub Pagesのカスタムドメイン設定(`markharness.com`)を新リポジトリ側で再設定する。DNS側(CNAMEレコード)は既存のまま流用できるが、リポジトリ側の「Pages有効化」設定は削除により失われるため、作り直した直後に再設定が必要。

### 不可逆な影響として認識しておくべき点

これは技術的に代替不可能な、削除に伴う既知の副作用であり、実行前に把握しておくべきもの。

- **スター・ウォッチ数・フォークとの関連付けが失われる**。削除→再作成は別リポジトリ扱いになるため、既存のスターやフォークはリセットされる。このリポジトリは公開から日が浅く(観測できたコミットは数日以内)実利用者数は少ないと推測されるが、実際の数はGitHub API制限によりこのセッションからは確認できなかった。削除前に、リポジトリのInsights(Stargazers / Forks / Traffic)を確認し、許容できる規模かを判断することを推奨する。
- **既存のRelease配布物(バイナリ)を既にダウンロードした利用者がいる場合、そのバイナリにはkakasi(GPL-3.0)問題が残ったままになる**。リポジトリを削除してもダウンロード済みバイナリは回収できない。実害は小さいと考えられるが(実験段階の宣言済みソフトウェア)、ゼロではない。
- **既存リポジトリへの外部リンク(ブログ記事・SNS投稿・crates.io等)があれば404になる**。現時点でそのような外部参照の有無は確認できていない。

## 検討したが採用しない選択肢

- **二リポジトリ構成の維持 + 同期自動化**: 実現可能だが、単一リポジトリ化と比べて「開発履歴の透明性」という利点を得られない。同期の自動化コストをかけるなら、単一リポジトリ化の方が構造的に単純で、かつ効果が大きい。
- **GitHub Wiki の採用**: 現時点でコミュニティ知見の蓄積がなく、PRレビューを経ない編集フローがプロジェクトの品質規律と一貫しない。将来的にDiscussionsで再検討する。
- **プロジェクト全体をGPL-3.0化**: kakasi問題の解決策として検討したが、利用者側に強い制約(派生物のソース開示義務)を課し、CLIツールとしての採用障壁を上げるため不採用。依存の置き換えを優先する。
- **既存公開リポジトリをそのまま整形して使う(force-pushでの履歴書き換え等)**: 既存履歴に価値が無いため、開発リポジトリの実履歴を土台にする方が結果的にシンプル。また既存リポジトリの設定(Pages、CNAME等)を保持できる利点はあるが、削除・再作成時の再設定コストは小さいため、この利点は決定的ではないと判断。
- **新規リポジトリの履歴を単一の初期コミットに圧縮する(スカッシュ)**: 開発の経緯を残す方がOSSとしての透明性に資するため不採用。ただし、開発リポジトリの初期段階に含まれる試行錯誤(テンプレート適用前後など)が多く、履歴として読みにくい場合は、`git filter-repo` で無意味な中間コミットのみを整理する余地はある。
