# 0038: GUIをコアから独立したプロジェクトとし、`markharness gui`は起動だけを担う

## ステータス

Proposed(2026-10-02)。実装は未着手。[0022](0022-remove-stage3-dashboard.md)(コアへのUI同梱の廃止)と[0032](0032-cli-read-model-seam.md)(CLIのJSONを外部契約とするseam)の方針を変えず、その上でGUIを作る形を決める。

## 背景

markharnessの関係(Requirement・Feature・Behavior・Scenario・TestCase)、Change Impact、Release Coverageを、人が画面で見られるGUIが必要になった。利用者には非開発者を含む。GUIの初版は閲覧が中心で、編集は将来の拡張として視野に入れる。

[0022](0022-remove-stage3-dashboard.md)は、コアに同梱していたdashboardを「MVPの命題に寄与しないUIの保守コストを恒常的に負う」として廃止した。[0032](0032-cli-read-model-seam.md)は、`traceability`・`impact`・`coverage`のJSONを外部向けの契約とし、表示は別ツールに委ねる方針を採った。今回、具体的な需要(非開発者向けの閲覧)と、フロントエンドの専任者が別に参加する開発体制が確定したため、GUIを作る形を決める。

先例は`git gui`である。Git公式マニュアルによれば、git-guiは独立プロジェクトとして保守され、安定版がGit本体の配布物に同梱される。起動は`git gui`というサブコマンドで、gitが別の実行ファイル`git-gui`を探して実行する。git-guiはgitの機能をgitのCLIを子プロセスとして呼ぶことで使い、実装言語もgit本体とは独立している。

## 決定

### 1. GUIはコアから独立したプロジェクトとする

GUIは別リポジトリ(`markharness-gui`)で、別の実行ファイル(`markharness-gui`)として作る。実装技術・画面設計・内部の構成は、GUIのリポジトリが決める。コアはそれを前提にしない。コアにHTTPサーバー・フロントエンドのアセット・ブラウザ起動の処理は置かない。

### 2. コアとの接点は、CLIが出力するJSONだけにする

GUIは`markharness`をGUIの外から子プロセスとして呼び、そのJSON出力だけを読む。`.markharness/`配下の内部ファイルは直接読まない。コアのRustライブラリを直接呼ぶこともしない。

初版が使うのは、既存の読み取り出力だけである: `traceability`(`--at`を省略した作業ツリー)、`binding list`、`coverage`、`impact`。軸・説明・手順などの詳細項目は既存の出力に無い。これらを画面に出すときは、先にCLIに読み取り出力を追加し、GUIはその出力を読む(初版の対象外)。`axes list`は初版で使わない。出力が`schema_version`を持たない裸の配列で、決定5の版の判断を適用できず、`traceability`には要素ごとの軸も無いため、初版に使い道が無い。

### 3. `markharness gui`は起動だけを担う

```
markharness gui [--dir <path>]
```

- 他のコマンドと同じく`project_root::resolve`で対象プロジェクトのルートを決める。未初期化なら`markharness init`を促すエラーにする。
- 実行ファイル`markharness-gui`を、`markharness`自身と同じディレクトリ、見つからなければ`PATH`の順に探して実行する。見つからなければ、GUIが同梱されていない旨と導入方法を示すエラーで終了する。
- GUIには`--dir <ルートの絶対パス>`を渡し、環境変数`MARKHARNESS_BIN`に、起動した`markharness`自身の絶対パスを設定する。GUIはこのパスの`markharness`を呼ぶ。GUIを単独で起動した場合に限り、`PATH`上の`markharness`を使う。同じ配布物の`markharness`だけを呼ばせて、版の食い違いを避けるためである。
- GUIの終了を待ち、その終了コードをそのまま返す。待つのは、起動の失敗やエラーをターミナルに見せ、`Ctrl-C`で終了できるようにするためである。GUI自身が常駐や別プロセス化をするかどうかは、GUIが決める。
- 任意の外部コマンドを呼ぶ汎用の仕組み(`markharness <name>`)にはしない。必要になるまで`gui`だけを持つ。

### 4. 配布は、CLIのみのアーカイブを変えず、GUI入りのアーカイブを別に追加する

CIやAIだけがCLIを使う場合に、GUIの分だけ配布物が大きくなるのを避けるため、現行のCLIのみのアーカイブはそのまま残す。GUI入りのアーカイブを別に作り、`markharness`と`markharness-gui`を同じディレクトリに入れる。GUIの成果物は、GUIリポジトリが公開した安定版を、`markharness`のリリース時に固定して取り込む。CLIのみの配布物で`markharness gui`を実行したときは、決定3の未同梱エラーになる。

### 5. 版の互換は、JSONの`schema_version`で判断する

GUIは、受け取ったJSONの`record_kind`と`schema_version`を確認し、対応していない版を検出したときは表示を止める。対応する版と受け取った版を示して更新を案内し、部分的な表示はしない。誤った関係を表示するより、止めるほうが害が小さいためである。

`schema_version`を上げる基準(出力へのフィールドや要素の追加を互換とみなすか)は、公開JSON全体にかかわるコアの方針である。[0025](0025-v2-forward-compatible-evolution.md)は公開JSONが`schema_version`を持つことまでを定めており、この基準は現時点でどのADRにも定められていない。本ADRでは決めず、コア側で別に決める。それが決まるまでの間、GUIは`schema_version`が対応する版と一致しない場合に止まる。

### 6. CLIのエラー形式は統一しない

GUIは、終了コードが0以外であれば失敗とみなし、標準エラー出力の文面をそのまま表示する。コマンドによってエラーがJSONのことと平文のことがあるが、GUIが機械的に分岐したい具体的な場面がまだ無いため、統一しない。

### 7. StrictDocの要求の表示情報は、GUIが`strictdoc export`を実行して得る

`source: external`のRequirementについて、`traceability`が返すのは`source_key`までで、要求の見出しや階層は含まれない。これらを画面に出すために、GUIが`strictdoc export --formats=json`を実行し、そのJSONを読む。これは、コアが外部の内容を保持・複製しない方針([0023](0023-requirement-native-and-external-source.md))と、コアは`strictdoc`を実行しない決定([0036](0036-knowledge-intent-from-strictdoc.md)決定2)を保つための、GUIだけの例外である。StrictDocは任意の連携のままで、無い環境ではmarkharnessのデータだけを表示する。

エクスポートには時間がかかる(後述の計測)。GUIは、エクスポートのJSONを基準として保存し、StrictDocのドキュメントと設定ファイルの更新時刻がそのJSONより新しいときだけ、裏で再エクスポートする。この間も、markharness側のデータは先に表示する。コアが課す制約は1つだけである: **古い内容を見せ続けない。利用者が、古い表示から必ず抜け出せる手段(キャッシュを使わない再エクスポート)を持つ。** 保存場所・判定の細部・更新中の表示は、GUIのリポジトリが決める。

### 8. 表示の更新は、手動の更新操作で行う

GUIはファイルを監視しない。利用者が更新操作をしたときに、JSONを再取得する。GUI自身が書き込み(編集)を行った後は、GUIが自動で再取得する(編集機能を持つ段階の方針)。GUIの外で起きた変更は、更新操作で反映する。

### 9. 初期スコープに含めないもの

- ターミナルを使わない起動(ダブルクリック、フォルダ選択画面、スタートメニュー)。必要になった場合は、別のデスクトップ版として別プロジェクトにし、このコアへの影響を小さく保つ。
- コミット済みの特定の版を見るための、レビュー用スナップショット(CIが生成したStrictDocのエクスポートを受け取る仕組みを含む)。版の識別情報を含めて、別に設計する。単独のオプションとしては追加しない。
- GUIからの編集。

## 影響範囲

- `src/cli.rs`: `Gui`サブコマンドの追加。起動のためのファイル探索と引数・環境変数の組み立ては、テストできる単位に分ける。実装は別タスクで、TDDで行う。
- `.github/workflows/release.yml`: GUI入りアーカイブの追加。GUIリポジトリに最初の安定版ができてから、取り込み方法を決める。
- `docs/ja/cli-manual.md`・`docs/en/cli-manual.md`: `markharness gui`の説明を、実装と同時に追加する。
- `CONTEXT.md`: 用語「GUI」(追加済み)。
- **変更しない**: 既存のADR(0022・0032・0033を含む)と設計書。[0022](0022-remove-stage3-dashboard.md)とは矛盾しない。コアにUIのコードを入れず、別プロジェクトの成果物を配布物に同梱するだけだからである。

## 検討したが採用しない選択肢

- **CLIのバイナリにGUI(ローカルWebサーバーとアセット)を埋め込む**: 配布は単一のバイナリで済むが、コアの責務・依存・リリースの頻度がUIの変更に引きずられる。フロントエンドのビルド(Node)がコアの開発に入る。[0022](0022-remove-stage3-dashboard.md)が避けた保守コストをコアが再び負う。
- **GUIをコアと同じリポジトリのワークスペースに置く**: CLIの契約の変更とGUIの修正を1つのPRで出せる利点がある。しかし、フロントエンド専任者が別に参加する体制では、独立した履歴・規約・ツールチェインの利点が上回る。
- **同梱せず、`PATH`の探索だけで起動する**: 非開発者に別のインストールと版の食い違いを負わせる。
- **GUIがコアのRustライブラリを直接呼ぶ**: 子プロセス起動のコストを避けられるが、GUIが内部APIに依存し、決定2の「JSONだけが契約」を崩す。閲覧中心の初版では、この利点が必要になる場面が無い。
- **エクスポート済みファイルを渡す`--strictdoc-export`オプションを初版に入れる**: CIが生成したファイルを渡す用途は、版の識別情報が無いと、古いエクスポートと新しいKnowledgeを組み合わせた誤った図を正常な画面として表示しうる。必要な場面は決定9の「レビュー用スナップショット」で、単独のオプションとして足す理由が今は無い。
- **毎回再エクスポートし、キャッシュを持たない**: 判定の実装は不要になるが、ソースコード連携を使うプロジェクトでは1回あたり約20秒かかる(後述)。
- **コアが外部要求の表示情報をCLIの出力として返す**: GUIが`strictdoc`を呼ぶ必要がなくなるが、[0023](0023-requirement-native-and-external-source.md)が意図的に定めた「コアは外部の内容を保持・複製しない」境界を曲げる。
- **ファイル監視による自動更新**: 実装(特にWindows)が過剰である。[0033](0033-traceability-defaults-to-working-tree.md)のとおり`traceability`は既定で作業ツリーを読むため、再取得すれば最新が得られる。

## 参考: `strictdoc export --formats=json`の所要時間

2026-10-02に、strictdoc 0.30.1・Windowsで計測した。1環境・実プロジェクト1件のみの計測であり、Linux・macOSでは測っていない。

| 対象 | 要求数 | 既定 | `--no-parallelization` |
|---|---|---|---|
| 合成データ(単純な要求、`.sdoc`8個) | 400 | 4.1秒 | 2.0秒 |
| StrictDoc自身のリポジトリ全体(`strictdoc export .`) | 358 | 20.6秒 | 18.6秒 |
| 同じ`docs/`と`spec/`だけを切り出したコピー | 358 | 6.3秒 | 3.9秒 |

- 遅さの主因は要求の数ではなく、設定の`include_source_paths`で指定されたソースコード側のトレーサビリティの走査である。この走査は、GUIが必要とする要求の見出しと階層には不要である。
- `--no-parallelization`は、小規模では所要時間を約半分にし、全体では約1割短くした。JSONの内容は、確認した2つのデータで両方式が同一だった。このオプションはStrictDoc自身のヘルプで「デバッグに有用」と説明されたものである。
- ソースコード連携を省く(`strictdoc export --config`で設定を上書きするなど)ことは、未検証の可能性である。StrictDocの設定はPythonのコードで、プロジェクトの設定を部分的に変えるのは難しい可能性がある。

## 未決事項(GUIのリポジトリで決める)

- GUIの実行形態(ネイティブウィンドウ、小型サーバーとブラウザ、など)。非開発者が追加のインストールなしで使える、OSごとの自己完結した成果物であること。
- エクスポートの保存場所、更新時刻の比較の詳細(ファイルの削除の扱いを含む)、更新中の画面表示。
- GUI入りアーカイブへの、GUI成果物の取り込み方法(GUIリポジトリに最初の安定版ができてから決める)。
